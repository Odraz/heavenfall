3. Organize actual authorized acceptance observations: fresh solo each class, mixed-level human co-op, death/revive/reconnect/host exit, post-win updates, collected-account variation and readability/fatigue. Track observations against a specific code checkpoint.
4. Gather current full-content performance/loading and four-human crest evidence on the acceptance reference setup. Use the benchmark (`npm run bench`, extended to the rogue workload) once you've played the build and ask for it, plus human sessions; the unit and e2e suites run as usual. 5. Repair defects and observed dominated/boring choices, update owning rules for accepted tuning, and repeat only observations affected by the change. Preserve prior evidence where still applicable.
6. Present the exact branch SHA, completeness/evidence report, outstanding issues and final human play checklist. Record your acceptance if given. Prepare the merge and prior-main checkpoint, but perform no merge/push/deployment without the separate final instruction.
