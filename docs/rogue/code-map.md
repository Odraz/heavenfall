## First implementation contract after R0

R1 starts with the pure generator in a new `src/gen/` module (no DOM, no three.js, no `Math.random`), its stamping into the existing `DungeonDef`/`GameMap` structures and the `validateLevel` changes, with the old fixed dungeon left intact as a fixture. Then the room lifecycle replaces the linear arena loop (`sim.ts` arena countdown and the wave-list skip), then discovery and the map, then run-scoped identity in `start`, the snapshot header and input. Pickups and props are R2; durable profile writes are R3; action provenance and targeted ability requests are R4, which reserves nothing earlier milestones need.

The prepared R1 brief must name the exact new modules, data shapes, wire offsets and commit boundaries against the baseline produced by R0. That SHA doesn't exist yet; don't fabricate it or mark R1 prepared merely because this map exists.

## Decisions R0 records

Record the refreshed base SHA; the immutable prior playable checkpoint; baseline path allowlist; schema/protocol/rules/content-version owners; stable catalog/action/source IDs; module ownership; old fixture adapter; asset source/event aliases; and allowed verification. `schema` controls save migrations, protocol version controls wire layout, and rules/content identity pins simulation/generation behavior. A documentation revision is not a save schema bump.

R0 can proceed without new art, audio, builds or game sessions. Verification during implementation follows [implementation.md](implementation.md).
